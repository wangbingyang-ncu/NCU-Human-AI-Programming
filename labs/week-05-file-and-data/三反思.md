# 人机协同三反思 —— 实验五：单摆物理模拟器

> 课程模板要求的三段反思，以下内容均来自本周实验中真实发生的事件，非虚构。

## 1. 意图设计思考

【思考手记】在编写初始 Prompt 时，我特意做了两点约束：一是"单文件 index.html、纯原生 Canvas、零外部库"，避开了 CDN 加载失败的风险（本机命令行网络受限，这个约束事后看是救命条款）；二是限定了视觉基调（#1a1a24 深灰科技色）与初始参数（L=200px、g=9.8、45°），让 AI 有明确的验收边界，而不是开放式发挥。

同时我发现了一个 AI 没有主动指出、但我在验收环节必须追问的问题：**L=200px 是像素，g=9.8 是米/秒²，量纲不一致**——直接代公式会得到 28 秒一个来回的"慢动作"。最终采用"100px = 1 米"的比例尺方案解决。这让我意识到：意图定义不只是"我要什么"，还包括**替 AI 划定量纲、单位、验收标准这些它容易默认含糊过去的边界**。

## 2. 报错自愈思考

【思考手记】本次实验中控制台没有抛出过面向用户的报错（最终 console.error / console.warn 均为 0），但开发过程中出现了几次"没有报错信息、结果却不对"的隐性错误，比显式报错更难排查：

1. **提交署名未更新**：修改作者信息后用 `git commit --amend` 修订提交，发现作者仍是旧值——因为 amend 默认保留原作者。解决：加 `--reset-author` 参数重跑。教训：命令的"默认行为"本身就是一种隐藏 bug 源。
2. **无头浏览器时间不推进**：用 Edge 无头模式截图时，"已运行"始终显示 0.00s。起初怀疑页面代码有 bug，后来查证这是无头模式虚拟时间不推进 requestAnimationFrame 的已知特性，不是页面问题。解决：改用 CDP 协议连接真实浏览器，等真实时间流过 2.5 秒再读内部状态，得到 2.50s 的吻合结果。
3. **截图误读为"能量不守恒"**：低分辨率截图中能量数字看起来对不上，放大 3 倍核对后确认是我看错了数字（3.824 vs 3.924），实际守恒精确到 0.001 J。

我的修复路径是：**先用客观证据定位（直读页面内部状态、放大截图核对数值），再决定改什么**——而不是看到"结果不对"就让 AI 盲改代码。三次排查中 AI 承担了工具搭建和数值验证，但"怀疑什么、按什么顺序排查"的判断由我主导。

## 3. 人机协同哲学反思

【思考手记】如果按工作量粗算，AI 承担了约 90% 的代码产出：770 行 HTML/CSS/JS、RK4 数值积分器、Canvas 光效渲染、还有四个层次的自动化验证脚本。如果让我从零手写，这些内容可能一学期都写不完。

但有三件事 AI 替代不了我：

- **物理建模决策**：像素和米怎么换算、阻尼量程 0.000~0.010 "衰减极慢但忠实实现"还是"放宽量程更好玩"，这些取舍没有标准答案，取决于我想让这个作品表达什么；
- **验收标准的定义**：什么叫"摆动流畅"？我把验收锚定在"周期与椭圆积分理论值误差 < 0.01%、能量漂移 < 10⁻⁸、真实浏览器 60fps"这些可证伪的指标上，AI 才有了努力方向；
- **对结果的最终判断**：AI 一度把"能量不守恒"当成真问题报告给我，是我放大截图核对后判定这是误报。**工具可以很聪明，但"信不信这个结果"的责任在我。**

一句话总结：AI 是极其高效的执行者和验证器，而我是这场创造中的意图源头、证据仲裁者和最终把关人——两者缺一，这份作业要么写不完，要么不可信。
